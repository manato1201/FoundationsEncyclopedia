## 概要

チームでGitを使うとき、どのブランチを作り、どうmainへ統合するかのルールが**ブランチ戦略**。代表的な型がいくつかあり、リリースの頻度やテストの自動化の度合いで、向き不向きがある。

## 基礎文法

| 型 | 特徴 | 向く場面 |
| --- | --- | --- |
| Git Flow | developやreleaseなど、役割ごとにブランチを分ける | 定期的なリリース、複数バージョンの保守 |
| GitHub Flow | mainと、機能ごとの短いブランチだけ | 継続的に公開するWebサービス |
| トランクベース | mainへ小まめに統合する | 自動テストが整った、頻繁なリリース |

## つまずきやすい点

- 型を厳密に真似することが目的ではない。チームに合わない手間は、省いてよい
- ブランチを長く生かすほど、統合時の競合が大きくなる。短い期間で統合する
- ルールを決めても、書いて共有しないと、守られない。READMEなどにまとめる

## 実装例(コード)

```bash
# GitHub Flowの流れ
git switch -c feature/login   # 機能ごとにブランチを作る
git push -u origin feature/login
# プルリクエストでレビューして、mainへ統合する
```
