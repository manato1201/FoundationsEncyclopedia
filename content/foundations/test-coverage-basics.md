## 概要

テストカバレッジは、テストを実行した際に、対象のコードのどれだけの割合(行、分岐、関数等の単位)が実際に実行されたかを示す指標。「カバレッジ80%」のような数値目標がプロジェクトで設定されることがあるが、この数値は「テストの網羅範囲」を示すものであり、「テストの品質」そのものを保証するものではない。

## 基礎文法

主なカバレッジの種類:

- **行カバレッジ**: コードの各行が1回でも実行されたか
- **分岐カバレッジ**: `if`文の各分岐(true/false両方)が実行されたか
- **関数カバレッジ**: 各関数が1回でも呼び出されたか

```bash
# Jestでのカバレッジ計測例
npx jest --coverage
```

## つまずきやすい点

- カバレッジ100%であっても、`expect`による検証を伴わない(ただ実行しただけの)テストであれば、バグを検出する能力はほぼゼロに等しい。「コードが実行されたこと」と「コードの振る舞いが正しいことを検証したこと」は別物
- カバレッジの数値目標を過度に重視すると、無意味なテスト(検証内容の薄いテスト)を量産して数字だけを達成しようとする逆効果が起きることがある。数値はあくまで「テストが薄い箇所を見つける手がかり」として使うのが健全
- 100%のカバレッジを目指すコストは、カバレッジが上がるにつれて指数関数的に増えていく傾向がある。エラーハンドリングの中でもまず起こりえないような防御的なコードまで無理に網羅しようとすると、テストの維持コストが実利を上回ることがある

## 実装例(コード)

```json
// カバレッジの最低ラインをCIで強制する設定例(package.json)
{
  "jest": {
    "coverageThreshold": {
      "global": { "branches": 70, "functions": 70 }
    }
  }
}
```
