## 概要

「動くコード」と「良いコード」は必ずしも一致しない。コードは書く時間より読まれる時間の方が長いことが多く、可読性の高いコードは、バグの発見・修正・機能追加のコストを下げる。特別な理論というより、いくつかの基本的な習慣の積み重ねで実現される。

## 基礎文法

代表的な習慣:

- **意図が伝わる命名**: `d`ではなく`daysSinceLastLogin`のように、変数名だけで意味が伝わるようにする
- **小さな関数**: 1つの関数は1つのことだけを行うようにし、長すぎる関数は分割する
- **早期return**: ネストした`if`文を避け、条件を満たさない場合は早めに関数を抜ける(ガード節)
- **マジックナンバーを避ける**: `if (age > 18)`ではなく`if (age > ADULT_AGE)`のように、意味のある名前を持つ定数にする

## つまずきやすい点

- コメントを書けば可読性が上がるとは限らない。コードの意図が変数名・関数名から読み取れるなら、コメントはむしろ「コードと重複する情報」として保守コストを増やすことがある。コメントは「なぜそうしたか」(WHYの説明)に絞るのが効果的
- 過度な抽象化・共通化は、かえって可読性を下げることがある。「3回同じコードが出てきたら初めて共通化を検討する」というような目安を持ち、早すぎる抽象化を避けるのも重要な判断
- 「きれいなコード」の基準はチームやプロジェクトによって異なりうる。個人の好みだけで判断せず、チームで合意したコーディング規約やLinterの設定に沿って一貫性を保つことが、複数人での開発では特に重要になる

## 実装例(コード)

```typescript
// 早期returnで条件分岐のネストを浅く保つ例
function getDiscountRate(user: User): number {
  if (!user.isActive) return 0;
  if (user.membershipYears < 1) return 0.05;
  return 0.1;
}
```
