## 概要

プルリクエスト(PR、GitLabではマージリクエストと呼ばれる)は、あるブランチの変更を別のブランチ(通常は`main`)に統合する前に、レビュー・議論・自動テストの実行といったプロセスを挟むための仕組み。GitHub・GitLab・Bitbucketなど多くのホスティングサービスが標準機能として提供している。

## 基礎文法

典型的なプルリクエストのワークフロー:

1. `main`から新しいブランチを作成し、変更をコミットする
2. リモートリポジトリへpushし、プルリクエストを作成する
3. レビュアーがコードを確認し、コメント・修正依頼・承認を行う
4. 必要な修正を重ね、承認とCIのパス([CIパイプラインの基本ステージ](/foundations/ci-pipeline-basics))が揃ったら`main`へマージする

## つまずきやすい点

- 1つのプルリクエストに複数の無関係な変更を詰め込むと、レビュアーが変更の意図を把握しづらくなり、レビューの質が下がる。「1つのPRは1つの目的に対応させる」という原則を守ると、レビューも履歴の追跡もしやすくなる
- レビューコメントへの対応として新しいコミットを積み重ねるか、既存のコミットを修正して上書きするかはチームの方針次第。頻繁に`force push`で履歴を書き換えると、レビュアーが「どこが新しく変わったのか」を追いにくくなることがある
- 承認(Approve)は「このコードに問題がない」という意思表示であり、レビュアーにも一定の責任が伴う。形式的に承認するだけのレビューが常態化すると、レビュープロセス自体が形骸化してしまう

## 実装例(コード)

```bash
# GitHub CLIを使ってプルリクエストを作成する例
gh pr create --title "機能Xを追加" --body "変更内容の説明..."
```
