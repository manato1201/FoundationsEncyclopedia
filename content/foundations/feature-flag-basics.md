## 概要

フィーチャーフラグ(機能フラグ)は、新機能のコードを本番環境にデプロイしつつ、実際にその機能を有効にするかどうかを、コードの再デプロイなしに切り替えられるようにする仕組み。「デプロイする」ことと「機能を公開する」ことを分離できるため、リスクを抑えた段階的なリリースが可能になる。

## 基礎文法

```typescript
if (featureFlags.isEnabled("new-catalog-ui")) {
  return <NewCatalogUI />;
} else {
  return <LegacyCatalogUI />;
}
```

- フラグの状態(有効/無効)は、コードとは別の場所(設定ファイル、外部の管理サービス等)で管理されることが多く、実行時に動的に切り替えられる

## つまずきやすい点

- フィーチャーフラグの数が増えすぎると、コード内に「有効な場合」「無効な場合」の分岐が大量に散らばり、可読性が大きく低下する。役目を終えたフラグ(完全にリリースされ、無効化する予定がなくなった機能)は、速やかにコードから削除する運用規律が重要
- 一部のユーザーだけにフラグを有効にする場合、フラグが有効なユーザーと無効なユーザーで異なるコードパスを通ることになり、テストすべき組み合わせが増える。全てのフラグの組み合わせを網羅的にテストするのは非現実的なため、リスクの高い組み合わせに絞ってテストする判断が必要になる
- フラグの状態をキャッシュしすぎると、フラグを切り替えたのに反映が遅れる(古いキャッシュを見続ける)ことがある。緊急に機能を無効化したい場面(不具合発覚時)では、この反映の遅延が問題になりうる

## 実装例(コード)

```typescript
// ユーザーの一部だけに新機能を有効化する例(段階的ロールアウト)
function isEnabledForUser(userId: string, rolloutPercentage: number): boolean {
  const hash = hashUserId(userId);
  return hash % 100 < rolloutPercentage;
}
```
