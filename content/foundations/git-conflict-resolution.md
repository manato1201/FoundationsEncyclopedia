## 概要

マージコンフリクト(競合)は、`merge`や`rebase`の際に、同じファイルの同じ箇所が両方の履歴で異なる形に変更されており、Gitが「どちらを採用すべきか」を自動的に判断できない状態。人間が手動でどちらを残す(または両方を組み合わせる)かを決める必要がある。

## 基礎文法

コンフリクトが起きたファイルには、以下のようなマーカーが挿入される:

```
<<<<<<< HEAD
現在のブランチ(自分側)の内容
=======
マージしようとしている側の内容
>>>>>>> feature-branch
```

解決の手順:

1. コンフリクトしたファイルを開き、マーカーを確認する
2. 残したい内容に書き換え、マーカー自体を削除する
3. `git add <ファイル>`でコンフリクト解決済みとしてマークする
4. `git commit`(mergeの場合)または`git rebase --continue`(rebaseの場合)で続行する

## つまずきやすい点

- マーカーの削除を忘れてそのままコミットしてしまうと、`<<<<<<<`のような文字列がコードやコンテンツにそのまま残ってしまう。コミット前に差分(`git diff --staged`)を確認する習慣が有効
- 「自分の変更を優先」「相手の変更を優先」を機械的に選ぶだけでなく、両方の意図を汲んで統合すべき場面が多い。特にロジックの変更が絡むコンフリクトは、周辺のコードを読んで意味を理解した上で解決する必要がある
- 頻繁にコンフリクトが起きるのは、同じファイルを長期間触り続ける複数のブランチが並行して存在している兆候であることが多い。ブランチのライフサイクルを短くする、こまめに`main`を取り込むといった運用面の対策も有効

## 実装例(コード)

```bash
# マージ中断してやり直したい場合
git merge --abort

# rebase中断してやり直したい場合
git rebase --abort
```
