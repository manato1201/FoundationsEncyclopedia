## 概要

コードレビューは、[プルリクエスト](/foundations/pull-request-basics)としてまとめられた変更を、本流にマージする前に他の開発者が確認するプロセス。バグの早期発見だけでなく、知識の共有・コーディング規約の維持・設計の一貫性の確保といった複数の目的を持つ。

## 基礎文法

レビューで確認する観点の例:

- **正しさ**: 意図した通りに動作するか、エッジケースを見落としていないか
- **可読性**: 他の開発者が読んで理解できるか、命名は適切か
- **設計**: 既存のアーキテクチャと整合しているか、過度に複雑になっていないか
- **テスト**: 変更に対応するテストが書かれているか

## つまずきやすい点

- レビューコメントが人格攻撃のように受け取られると、レビュー文化そのものが萎縮してしまう。「このコードのこの部分が」という対象を明確にし、代替案を添えるなど、建設的なフィードバックの書き方が重要になる
- 巨大な変更(数千行に及ぶプルリクエスト)は、レビュアーが全てを丁寧に確認しきれず、形式的な承認になりがち。変更を小さく分割してレビューしやすくすることが、レビューの質を保つ実務的な工夫になる
- 「レビュアーの好み」と「客観的な問題点」を混同したコメントは、レビューを不必要に長引かせることがある。プロジェクトでコーディング規約やスタイルガイドを明文化し、Linterのような自動チェックに任せられる部分は自動化しておくと、レビューの議論を本質的な問題に集中させられる

## 実装例(コード)

```bash
# GitHub CLIでプルリクエストにレビューコメントを付ける例
gh pr review 123 --comment --body "この関数の命名をより具体的にすると良さそうです"
```
