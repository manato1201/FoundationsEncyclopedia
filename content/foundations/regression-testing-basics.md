## 概要

回帰テスト(リグレッションテスト)は、コードに変更を加えた際、その変更が意図した箇所以外の既存機能を壊していないか(退行=リグレッションが起きていないか)を確認するために、既存のテスト群を再実行すること。[CIパイプラインの基本ステージ](/foundations/ci-pipeline-basics)で、コードのpushのたびにテストスイート全体を自動実行するのは、回帰テストを継続的に行っていることに他ならない。

## 基礎文法

回帰テストの典型的な流れ:

```
新しい変更をコミット
  → 既存の全テストスイートを実行
  → 全て成功すれば「既存機能を壊していない」とみなす
  → 1つでも失敗すれば、その変更が既存機能に影響を与えたと判断する
```

## つまずきやすい点

- バグを修正した際、そのバグを再現するテストケースを追加せずに修正だけを行うと、将来同じバグが再発しても気づけない(回帰テストの対象になっていない)ことがある。バグ修正時には「このバグを検出できるテスト」を合わせて追加するのが望ましい習慣
- テストスイートの実行時間が長くなりすぎると、コミットのたびに全テストを実行する運用が現実的でなくなる。変更の影響範囲を分析して関連するテストだけを実行する(影響分析に基づく選択実行)仕組みを導入する場合もある
- 回帰テストが「たまに失敗する」不安定なテスト(flakyテスト)を含んでいると、本当の回帰(バグの再発)なのか、テスト自体の不安定さによる偶発的な失敗なのかを見分けるコストが発生する。flakyテストは早期に修正・削除するのが、テストスイート全体への信頼を保つ上で重要

## 実装例(コード)

```typescript
// バグ修正と同時に、そのバグを再現するテストケースを追加する例
test("空配列でのソートはエラーにならない(過去に発生したバグの回帰テスト)", () => {
  expect(() => sortEntries([])).not.toThrow();
});
```
