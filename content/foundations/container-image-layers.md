## 概要

コンテナイメージは、単一の巨大なファイルではなく、[Dockerfile](/foundations/dockerfile-basics)の各命令ごとに生成される「レイヤー」(差分)を積み重ねた構造を持つ。同じベースイメージを使う複数のイメージ間でレイヤーを共有できるため、ディスク容量や転送量を節約できる。

## 基礎文法

```dockerfile
FROM node:20-alpine   # レイヤー1: ベースイメージ
WORKDIR /app           # レイヤー2: 作業ディレクトリの変更
COPY package.json ./   # レイヤー3: ファイルの追加
RUN npm install         # レイヤー4: 依存関係のインストール(この結果もレイヤーとして保存される)
COPY . .                # レイヤー5: 残りのファイルの追加
```

各命令の結果はキャッシュされ、Dockerfileのある行より前が変わっていなければ、その行以降だけが再実行される。

## つまずきやすい点

- レイヤーのキャッシュは「その命令とその前の全レイヤーが完全に同じ場合」にのみヒットする。`COPY . .`のようにアプリケーションコード全体をコピーする命令を早い段階に置いてしまうと、コードの些細な変更のたびにそれ以降の全レイヤー(依存関係のインストール含む)が再実行され、ビルド時間が大きく伸びてしまう
- 各レイヤーは削除しても完全にはイメージサイズから消えない(以前のレイヤーとして残り続ける)。「一時ファイルを作って、同じレイヤー内で削除する」ように`RUN`をまとめて書かないと、実際には存在しないはずのファイルがイメージのサイズに残り続けることがある
- ベースイメージの選択(`node:20`のフルサイズ版か`node:20-alpine`のような軽量版か)は、レイヤーの土台部分のサイズに直結する。軽量版は起動・転送が速い代わりに、含まれるシステムライブラリが少なく、一部のネイティブモジュールのビルドで問題が起きることがある

## 実装例(コード)

```dockerfile
# 悪い例: 一時ファイルが別レイヤーに残ってしまう
RUN wget https://example.com/large-file.zip
RUN unzip large-file.zip && rm large-file.zip

# 良い例: 同じRUN内でダウンロード・展開・削除を完結させる
RUN wget https://example.com/large-file.zip \
    && unzip large-file.zip \
    && rm large-file.zip
```
