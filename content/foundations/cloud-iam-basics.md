## 概要

クラウドでは、サーバー・データベース・ストレージなど、多くのリソースを、インターネット越しに操作する。誰でも何でもできる状態は危険なので、**IAM**(Identity and Access Management)で、権限を管理する。考え方は、[最小権限の原則](/foundations/least-privilege-principle)が基本。サービスごとに用語は違うが、「主体・操作・対象」で考える点は共通している。

## 基礎文法

| 用語 | 意味 |
| --- | --- |
| プリンシパル | 操作する主体(人・アプリ・サービス) |
| ポリシー | 許可・拒否の規則を書いた文書 |
| ロール | 一時的に引き受ける権限のまとまり。アプリやサーバーに付ける |
| グループ | 人のユーザーを束ねて、まとめて権限を付ける単位 |

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject"],
      "Resource": "arn:aws:s3:::example-bucket/*"
    }
  ]
}
```

上は、AWSのポリシーの書き方の例で、「`example-bucket`の中身を読むことだけを許可する」という意味。他のクラウドでも、用語や書式は違うが、同じ考え方で設定する。

## つまずきやすい点

- 動かないときに、全権限(管理者権限)を付けて解決したことにしない。必要な権限だけを足していく
- 長期に使えるアクセスキーは、漏れると被害が大きい。アプリやサーバーには、ロールで一時的な認証情報を使う方式が推奨される
- 人のユーザーには、多要素認証を有効にする([多要素認証の基礎](/foundations/mfa-basics))
- ワイルドカード(`*`)で広く許可すると、意図しない範囲にまで権限が及ぶ。対象のリソースを、具体的に指定する

## 実装例(コード)

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::example-bucket/uploads/*"
    },
    {
      "Effect": "Deny",
      "Action": "s3:DeleteObject",
      "Resource": "arn:aws:s3:::example-bucket/*"
    }
  ]
}
```
