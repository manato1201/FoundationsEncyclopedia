## 概要

Javaのガベージコレクション(GC)は、プログラムからもう参照されなくなった(到達不能な)オブジェクトを自動的に検出し、そのメモリを解放する仕組み。C/C++のように明示的な`free`/`delete`を書く必要がない一方、GCの動作タイミングや挙動を理解していないとパフォーマンス問題の原因が見えにくくなる。

## 基礎文法

Javaのヒープは世代別に管理されることが多い(世代別GC):

- **Young世代**: 新しく生成されたオブジェクトが最初に置かれる領域。ほとんどのオブジェクトはすぐに不要になるという経験則に基づき、頻繁かつ高速にGCが行われる(Minor GC)
- **Old世代**: Young世代のGCを何度も生き延びた、寿命の長いオブジェクトが移動する領域。GCの頻度は低いが、1回のGCにかかる時間は長くなりやすい(Major/Full GC)

## つまずきやすい点

- 「参照が切れたら即座にメモリが解放される」わけではない。GCは一定のタイミングでまとめて到達可能性を再計算するため、解放にはタイムラグがある
- 短命なオブジェクトを大量に生成し続ける実装(ループの中で毎回新しいオブジェクトを作る等)は、Young世代のGC頻度を上げ、全体のスループットを下げる原因になりやすい。ゲームのようにフレームごとの安定性が重要な用途では、オブジェクトの使い回し(プーリング)で生成そのものを減らす対策が有効
- GCの一時停止(Stop-The-World)がアプリケーションの応答性に影響することがある。低遅延が求められる用途では、GCアルゴリズムの選択(G1、ZGC等)や設定のチューニングが必要になる場合がある

## 実装例(コード)

```java
// オブジェクトプールの簡易例: 生成コストとGC負荷を避けるため使い回す
class BulletPool {
    private final Deque<Bullet> pool = new ArrayDeque<>();

    Bullet rent() {
        return pool.isEmpty() ? new Bullet() : pool.pop();
    }

    void giveBack(Bullet bullet) {
        pool.push(bullet);
    }
}
```
